Consistency Check

October 25, 2026 — the auditor that reads the site and files tickets about it

How it works

Two layers. First a deterministic scanner runs — pure python, no deps, catches the mechanical stuff exactly the same way every time. Then a headless pi agent reads the site the way a human would and looks for what rules can't catch. The agent is read-only by instruction; it never fixes anything, it only reports, and the wrapper files the ticket. The cards below describe both layers.

Judgment checks — the pi agent

Styling drift between similar pages, inconsistent date or title formats, pages missing from (or duplicated in) the blog index, navigation/footers/meta tags that don't match, and docs that contradict the code they describe. The agent runs the scanner first as its baseline, then adds what a human eye would notice. Runs get a fresh context every time — no memory, no drift in how it judges.

Card titles vs post headings

Every card on the blog index must match the <h1> of the post it links to — including capitalisation. This catches posts whose index card says something the post itself doesn't.

Undefined CSS classes

Any class used in markup must be defined in the page's stylesheet. This is the bug that made the medieval-animals card render in body colour instead of the purple title colour: someone renamed a card's class="title" to a .cmd class that was never styled.

Missing dates

Blog index cards should carry a date. A card without one breaks the pattern of every other card on the page.

Broken internal links

Every internal href/src must resolve to a real file. Paths that Caddy proxies or redirects elsewhere (like /adsplosion or /tickets) are excluded so they don't cause false positives.

Heading structure

Exactly one <h1> per page — two means a page has two "titles", which usually means something was pasted in twice.

False-positive defence

The scanner parses HTML with a real parser (not string matching), so escaped markup inside rendered agent transcripts — like &lt;span class="cmd"&gt; in the logs page — is never mistaken for real markup.

What happens on a finding

bash — 80×24
findings → GitHub ticket, label: backlog   (deduplicated — a rerun updates the existing ticket)
backlog  → you triage: read   → the ticket loop picks it up and fixes it
review   → you close it: done

The agent never fixes anything itself — it only reports. Full ticket workflow: the ticket loop.

When it runs

On a schedule, plus on demand — runs are controlled from the server itself and from the private admin pages, not from this public page. Results always land the same way: as a backlog ticket on GitHub, so every finding has an audit trail. Nothing found → no ticket, no noise.
