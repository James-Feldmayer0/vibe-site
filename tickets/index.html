How the Ticket Loop Works

The poller — ticket-daemon.sh

A systemd service (ticket-loop.service) runs a bash loop that wakes every 30 seconds, lists open issues on James-Feldmayer0/Adsplosion via the GitHub API, and skips anything that's a PR. No new tickets → one cheap API call, zero tokens, back to sleep.

The dispatcher — headless pi

Each new issue is handed to a headless pi -p run: an AI agent with shell access, the site files, the repo, and the GitHub token. It reads the ticket, makes the change, and talks back to the issue it came from.

The Flow

ticket-loop.sh — poll cycle
# every 30 seconds:
1. fetch  GET /issues?state=open   (PRs filtered out)
2. guard  flock — a slow run never overlaps the next poll
3. dispatch pi -p (one agent session per ticket, with rules)
4. agent   implement → verify live → comment on the issue
5. close   state=closed, state_reason=completed — only if verified

Guardrails

Verify before close

The agent must check its own work — curl the live site or run the app — before a ticket may be closed. No "edited the file, done."

Never guesses

Ambiguous ticket? The agent posts a comment asking for clarification and stops — it does not close, and it does not improvise a guess.

Attempt cap

Each ticket gets max 2 agent attempts. Repeated failures leave the issue open and untouched, flagged for a human.

Scope discipline

Site pages (/var/www/vibe) deploy directly; repo changes are committed and pushed via SSH. Unrelated systems stay untouched.

Ops

# commands
systemctl status ticket-loop   # is it alive?
tail -f /root/ticket-loop.log  # watch polls live

Failures

/logs — the failure board

Every poll cycle pumps the poller log, service journal, and agent transcripts to /logs — regenerated automatically, so it's never more than 30 seconds stale. Failures show as a red banner; historic ones stay highlighted but don't trip the alarm. Secrets are redacted.
