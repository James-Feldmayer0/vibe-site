How the Ticket Loop Works

The poller — ticket-daemon.sh

A systemd service (ticket-loop.service) runs a bash loop that wakes every 30 seconds, lists open issues on James-Feldmayer0/Adsplosion via the GitHub API, and skips anything that's a PR — or anything not labeled read. Tickets filed in backlog sit untouched until a human triages them. No new tickets → one cheap API call, zero tokens, back to sleep.

The dispatcher — headless pi

Each new issue is handed to a headless pi -p run: an AI agent with shell access, the site files, the repo, and the GitHub token. It reads the ticket, makes the change, and talks back to the issue it came from.

Fresh context per ticket: every run starts with --no-session, so each ticket gets a clean, empty context — nothing carries over from previous tickets. This keeps prompts small and saves tokens: the agent only ever pays for its own ticket, never the history of every run before it.

The Workflow

ticket lifecycle — GitHub labels
backlog      filed, not triaged — the loop will not touch it
  │ human triages
read         ready — the loop picks these up, nothing else
  │ loop
in progress  agent is working on it (fresh context per ticket)
  │ agent, after live verification
review       done & verified by the agent — still open, waiting on a human
  │ human closes
done
ticket-loop.sh — poll cycle
# every 30 seconds:
1. fetch  GET /issues?state=open   (PRs + non-“read” filtered out)
2. guard  flock — a slow run never overlaps the next poll
3. label  read → in progress
4. dispatch pi -p (one agent session per ticket, fresh context each run)
5. agent   implement → verify live → comment on the issue
6. label   in progress → review — only if verified; a human closes it

Guardrails

Verify before review

The agent must check its own work — curl the live site or run the app — before a ticket may move to review. No "edited the file, done." And it never closes tickets: closing is the human's call.

Never guesses

Ambiguous ticket? The agent posts a comment asking for clarification and stops — labels stay on in progress and it does not improvise a guess.

Attempt cap

Each ticket gets max 2 agent attempts. Repeated failures leave the issue open and untouched, flagged for a human.

Scope discipline

Site pages (/var/www/vibe) deploy directly; repo changes are committed and pushed via SSH. Unrelated systems stay untouched.

The Consistency Check

A headless pi agent audits the whole site. It starts with a deterministic scanner — pure python, no deps: index card titles vs post <h1>s, CSS classes used but never defined (the bug that made one blog card render in the wrong colour), missing dates, broken internal links, duplicate <h1>s — then reads the site the way a human would, looking for what rules can't catch: styling drift between pages, inconsistent date formats, docs that contradict the code they describe. It knows which paths Caddy proxies or redirects, so those aren't false positives, and it parses HTML with a real parser so escaped markup inside rendered transcripts can't fool it. The agent never fixes anything — it files a backlog ticket, deduplicated so a rerun updates the existing ticket instead of opening a new one. Nothing found → no ticket, no noise. Runs on demand or on a schedule, controlled from a private admin page on this box.

Failures

/logs — the failure board

Every poll cycle pumps the poller log, service journal, and agent transcripts to the /hidden/logs page — regenerated automatically, so it's never more than 30 seconds stale. Failures show as a red banner; historic ones stay highlighted but don't trip the alarm. Secrets are redacted.
